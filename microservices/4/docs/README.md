Kubernetes и HashiCorp Vault
### 1. Поддержка контейнеров
Основной платформой решения выступает **Kubernetes (K8s)** — лидер в области оркестрации контейнерных приложений. Kubernetes берет на себя ответственность за планирование рабочей нагрузки, запуск контейнеров (на базе Docker, containerd или других сред выполнения) на физических или виртуальных узлах кластера и поддержание их работоспособности,.

Минимальной рабочей единицей в Kubernetes является **Под (Pod)**, в котором может быть запущен один или несколько тесно связанных контейнеров, делящих общую сеть и хранилище.

### 2. Обнаружение сервисов и маршрутизация запросов
Для организации связи между приложениями и маршрутизации используются следующие сущности Kubernetes:
*   **Сервисы (Services):** Обеспечивают абстракцию над подами приложения. Сервис получает собственный стабильный IP-адрес или DNS-имя и автоматически распределяет сетевой трафик между здоровыми экземплярами подов,. Сервисы используют механизм селекторов меток, чтобы динамически понимать, какие поды к ним относятся.
*   **Ingress и Ingress Controller:** Для маршрутизации внешнего HTTP- и HTTPS-трафика используется объект Ingress (например, в связке с NGINX Ingress Controller). Ingress позволяет настроить гибкие правила маршрутизации к внутренним сервисам на основе URL-путей или поддоменов (включая Wildcard Hosts) через единую внешнюю точку входа,.

### 3. Горизонтальное масштабирование
Ручное или базовое горизонтальное масштабирование в Kubernetes обеспечивается ресурсами **ReplicaSet** и **Deployment**. Они гарантируют, что в любой момент времени работает строго заданное количество экземпляров (реплик) приложения,. Если приложение требует больше ресурсов, вы можете увеличить желаемое число реплик, и Kubernetes автоматически распределит новые контейнеры по доступным узлам кластера.

### 4. Автоматическое масштабирование 
Для автоматической адаптации к изменяющейся нагрузке решение использует два уровня автоскейлинга:
*   **Horizontal Pod Autoscaler (HPA):** Отвечает за автоматическое изменение количества подов приложения. HPA непрерывно опрашивает метрики (например, потребление CPU и памяти через компонент Metrics Server) и, если нагрузка превышает заданные пороговые значения (например, CPU > 50%), автоматически добавляет новые поды, а при снижении нагрузки — удаляет их,,,.
*   **Cluster Autoscaler (CA):** Работает на инфраструктурном уровне. Если HPA запрашивает создание новых подов, но в кластере не хватает вычислительных ресурсов для их запуска, CA автоматически добавляет новые виртуальные или физические узлы (ноды). И наоборот, простаивающие узлы удаляются для экономии средств,.

### 5. Явное разделение ресурсов, доступных извне и внутри системы
Kubernetes обладает встроенными механизмами для строгой изоляции трафика:
*   **Изоляция доступа на уровне сервисов:** Внутренние приложения, такие как базы данных или скрытые микросервисы, публикуются через сервисы типа **ClusterIP**, которые доступны исключительно внутри кластера,. Публичные компоненты выводятся наружу через **Ingress** (для веб-трафика) или сервисы типа **LoadBalancer / NodePort**,,.
*   **Изоляция сети (Network Policies):** Для дополнительной безопасности применяются сетевые политики (Network Policies). Они позволяют гранулярно описать, какие поды имеют право обращаться друг к другу (Ingress-правила) и к каким внешним ресурсам разрешено делать запросы (Egress-правила),. Например, можно явно запретить прямое обращение извне к подам с базами данных или ограничить трафик между разными пространствами имён (namespaces),.

### 6. Конфигурация через переменные среды и безопасное хранение секретов
Всё управление конфигурацией выстраивается с учётом безопасности и принципов «Infrastructure as Code» (IaC):
*   **Обычная конфигурация:** Несекретные настройки передаются в поды через **ConfigMap** в виде переменных окружения. Это позволяет использовать один и тот же Docker-образ в разных средах (Dev, Test, Prod), просто меняя значения переменных,.
*   **Защищённое хранение секретов (HashiCorp Vault):** Для паролей, ключей шифрования и API-токенов де-факто стандартом является внешнее хранилище **HashiCorp Vault**. Оно обеспечивает безопасное хранение, поддержку динамических секретов, шифрование данных и подробный аудит,,.
*   **Доставка секретов в переменные среды приложения:** Чтобы безопасно передать данные из Vault в память приложения (в виде переменных окружения), предлагается использовать инструмент **Bank-Vaults Secret Injection Webhook**.
    * *Принцип работы:* Вместо того чтобы сохранять чувствительные данные в стандартные (и потенциально уязвимые для просмотра) k8s Secrets, инструмент работает как Webhook. В манифесте приложения вы указываете лишь ссылки на секреты в Vault. При запуске пода Webhook внедряет в контейнер специальную утилиту `vault-env`, которая выступает входной точкой (entrypoint). `vault-env` самостоятельно обращается в Vault за реальными значениями и подставляет их напрямую в переменные окружения процесса,.
    * Таким образом, секреты доставляются в память приложения безопасно и прозрачно, нигде не сохраняясь на диске или в манифестах кластера. Запрет команды `exec` в поды (отключение консольного доступа) защитит эти переменные среды от утечки из запущенного контейнера.
